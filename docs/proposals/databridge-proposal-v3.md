# 本科毕业设计选题方案（v3）

> **拟定题目：**《基于 Spring Boot 的异构数据库迁移与增量同步平台的设计与实现》
> **项目代号：**DataBridge
> **场景：**MySQL → PostgreSQL，单向、单机、中小规模
> **计划周期：**12 周，包含 1 周机动

## 一、选题定位

本课题研究一个具体而可验证的问题：如何在源库持续写入和进程可能中断的条件下，将 MySQL 表可靠地迁移到 PostgreSQL，并在全量迁移后持续同步变更。系统自研 JDBC 全量通道、检查点和目标写入逻辑，集成 Debezium Engine 采集 Binlog。Debezium 的 Binlog 解析机制不作为原创成果。

核心交付不是“支持尽可能多的数据库”，而是限定场景下的**全量—增量无空窗衔接、可恢复处理和最终一致性验证**。

## 二、范围和验收线

### 必做

1. 通过环境变量配置 MySQL、PostgreSQL 连接，提供连接检查与单表元数据读取；目标表由用户预先创建，建任务前检查字段和主键兼容性。
2. JDBC 单列有符号 BIGINT 主键 keyset 分页全量读取和 PostgreSQL 批量 UPSERT；开始时固定扫描主键上界。
3. 全量批次与检查点同事务提交；进程强制退出后从检查点恢复。
4. Debezium Engine 以 `no_data` 模式先建立 CDC 捕获，支持 INSERT、UPDATE、DELETE；事件先持久化，再确认处理。
5. 全量期间 CDC 不直接写业务目标表；全量完成后按事件顺序回放，再持续应用。
6. 事件去重；业务写入与事件应用游标同事务提交；异常重启后安全重放。
7. 源端停写、CDC 追平后的记录数和分块行数据校验，并定位差异。
8. 精简的任务状态、进度、错误信息及基础操作界面；Docker Compose 演示环境和自动化测试。

### 第一阶段明确限制

- 固定表结构；不处理运行中的 DDL、外键拓扑、触发器、副作用写入和双向同步。
- 表必须有单列、不可变、有符号 BIGINT 主键；无主键、复合主键、无符号超范围主键及主键更新任务直接拒绝。
- 同一目标表只允许一个同步任务；新任务要求目标表为空，恢复任务沿用既有目标和元数据。
- 第一阶段不在后台数据库保存连接密码；界面只选择和测试预配置的数据源。
- 不宣称跨数据库强一致或通用端到端 Exactly Once；验收目标是源端停写并追平后的目标状态一致。
- 自动建表、COPY、复合主键、在线校验、索引优化和更复杂的前端均为选做。

## 三、技术路线

| 模块 | 技术 | 责任 |
|---|---|---|
| 后端 | Java 21、Spring Boot、JDBC | API、任务状态、全量读取与写入、校验 |
| CDC | Debezium Engine、MySQL Connector | 捕获 Binlog 变更；不承担全量数据搬运 |
| 目标与元数据 | PostgreSQL | 业务表、检查点、CDC 事件、应用游标 |
| 前端 | Vue 3、Element Plus | 任务配置、状态和校验报告 |
| 环境与测试 | Docker Compose、JUnit、集成测试 | 固定数据库环境、故障注入和回归验证 |

MySQL 必须启用 Row 格式 Binlog，并配置完整行镜像和足够的日志保留期。Debezium 的 schema history 与 offset 需要持久化；选定依赖版本后在最小集成测试中验证 JDBC 存储方案。当前 Debezium 文档已将 `schema_only` 标为弃用，使用 `no_data`。[MySQL Connector 文档](https://debezium.io/documentation/reference/stable/connectors/mysql.html)、[状态存储文档](https://debezium.io/documentation/reference/stable/configuration/storage.html)

## 四、关键设计：全量与增量衔接

```text
MySQL ──Binlog──> Debezium ──持久化──> CDC event log
   │                                      │
   └──JDBC keyset 读取──> PG 业务表        │
                         全量完成后 <─────┘ 按序回放
                             │
                             └──────> 持续消费 event log
```

1. 任务校验表结构、目标表为空、Binlog 条件和主键限制。
2. 启动 Debezium `no_data` 捕获，确认初始 schema 与捕获位点已建立，然后才允许全量读取。
3. CDC 事件按源端顺序写入 PostgreSQL 的持久化事件表。事件写入成功后向 Engine 确认；源端位点的周期刷盘可能导致重放，因此事件有稳定唯一标识并去重。
4. 记录源表开始时的最大主键。全量仅扫描 `last_id < id <= high_watermark`，每批将 UPSERT 与 `last_id` 检查点同事务提交。
5. 全量完成后，从事件日志最早未应用事件开始按序回放。每批将业务写入与应用游标同事务提交；CDC 此时仍持续入日志。
6. 追平后进入持续同步。全量写入器不再运行，事件消费者始终是唯一的增量写入者。

**为什么需要隔离两条写入通道：**如果 CDC 已把某行更新为新值，而迟到的全量批次仍持有旧值，后者会覆盖前者；UPSERT 不解决写入先后顺序。先全量、后按序回放可使全量期间发生的增删改覆盖批次读取到的旧状态。

## 五、恢复与校验

- 全量崩溃：批次和检查点同事务回滚或同事务提交；恢复后从已提交检查点继续。
- CDC 捕获崩溃：事件入库后才确认处理；Debezium 位点尚未刷盘时会重发，事件唯一键去重。不得在失败时吞掉事件后继续确认。
- 事件应用崩溃：目标写入与应用游标同事务提交；恢复后从游标继续。首版保留事件日志，不在位点尚有重放风险时删除去重依据。
- Binlog 已被清理、schema history 丢失或类型不可映射：任务明确失败并要求人工处置，不自动重置位点并假装成功。
- 确定性校验：暂停源端写入，等待 CDC 已采集和已应用的队列追平；以相同主键范围读取两端，经 Java 端统一规范化后比较记录数与行哈希，逐行定位差异。

## 六、实验设计

| 实验 | 最低要求 | 指标 |
|---|---|---|
| 全量性能 | 1 万、10 万、100 万行；不同批次大小 | 耗时、行/秒、峰值内存 |
| 衔接正确性 | 全量期间持续插入、更新、删除；包括“CDC 先写、全量后写”的反例 | 停写追平后差异行数 = 0 |
| 故障恢复 | 在全量写入、CDC 事件入库和事件回放三个位置分别终止进程 | 恢复后差异行数 = 0、恢复耗时 |
| 类型边界 | 整数范围、DECIMAL、时间、Unicode、JSON、NULL | 正确行数、失败原因 |
| CDC 延迟 | 稳定负载下记录源端提交至目标可见时间 | P50、P95、P99 |
| 分块校验 | 人为修改目标行、删除目标行、添加多余行 | 检出与定位准确率 |

实验固定数据库版本、容器资源、表结构、索引和测试数据种子。每组至少运行三次，保留原始结果、参数与汇总脚本。持续写入时两端不在同一时刻读取，在线校验结果不作为最终一致性的证明。

## 七、12 周实施计划

| 周次 | 任务 | 验收 |
|---|---|---|
| 1 | 项目规则、设计确认、环境准备、真实 CDC 最小验证 | 能采集一次 INSERT/UPDATE/DELETE，版本固定 |
| 2 | 单表约束与元数据检查、CDC 事件可靠落库 | 重启后事件不丢失、重复可去重 |
| 3–4 | JDBC 全量、批量写入、同事务检查点 | 强制退出后可续传 |
| 5–6 | 全量—增量隔离、按序回放、持续同步 | 并发写入后停写追平，差异为零 |
| 7 | 三个故障窗口的专项测试和修复 | 多次中断后仍一致 |
| 8 | 确定性分块校验及差异报告 | 人为差异被准确定位 |
| 9 | 精简前端、任务操作与端到端演示 | 页面完成一次完整任务 |
| 10 | 正式性能、延迟及恢复实验 | 可复现实验结果与图表 |
| 11 | 机动、论文初稿与测试报告 | 核心代码冻结 |
| 12 | 论文修订、部署文档、答辩演示 | 一键部署并完成模拟答辩 |

第 2 周末如果真实 CDC 与持久化位点仍未验证通过，先暂停前端与性能功能；第 6 周末若衔接正确性未通过，不把“校验后手工修复”当作替代方案，而应先修复事件顺序与恢复逻辑。

## 八、预期成果

可运行的迁移同步系统、后端与基础前端代码、Docker Compose 环境、故障注入测试、可复现的实验数据与图表、设计文档、部署指南、毕业论文和答辩演示材料。
