# 全量复制性能实验设计（2026-10-20）

## 要回答的问题

在固定双库资源及固定表结构下，DataBridge 的 JDBC 全量通道面对 1 万、10 万、100 万行时，批次大小 500 与 1000 对运行时间、吞吐和 JVM 堆峰值有何影响？这是全量通道实验，不代表端到端 CDC 同步耗时。

## 实验单元与控制

- 因子：行数 `10000/100000/1000000`，批次 `500/1000`，每组 3 次，共 18 次正式运行；另做不计入结果的 1 万行预热。
- 每次生成新的任务 UUID、清空同一目标实验表；源表预先建好且在测量期间静止。计时从第一次 `copyNextBatch` 前开始，到返回零且检查点完成后结束；不含建表、种子导入、容器启动、校验扫描。
- 源端与目标端均为一次性 Testcontainers，镜像固定 MySQL 8.4.11、PostgreSQL 17.11，分别限制 2 CPU/2 GiB；一次运行内所有组共享同一对容器。每个规模用单独的 `id BIGINT PRIMARY KEY, name VARCHAR(64), amount DECIMAL(12,2)` 表。目标同构（`numeric(12,2)`）。
- 用固定随机种子 20261020 打乱 18 次运行顺序，避免批次/规模与时间漂移完全重合；保留顺序号、行数、批次、重复号。没有跨机器或跨日独立重复，三次是同一环境内技术重复，结论仅适用于这个实验环境。
- 成功条件：目标行数等于源行数、检查点 `completed=true`、`last_id` 等于期望最大主键；任一失败中止，不写入“成功结果”。

## 采样与输出

- 每次记录墙钟 `elapsed_ms`、`rows_per_second`、JVM 各堆池 peak used 合计、运行顺序和 UTC 时间；峰值包含 JUnit/JDBC 等进程活动，不解释为 FullCopyWorker 独占内存。
- 运行中的原始逐次 CSV 位于忽略目录 `experiments/raw/`，每次运行使用带 UTC 时间的唯一文件，失败保留已写入的行。完整 18 条核对通过后，将这份小体量测量记录另存为受版本控制的 `experiments/full-copy-runs.csv`；汇总脚本验证每组恰有 3 次记录，再计算中位数、最小/最大值和均值，提交 `experiments/full-copy-summary.csv` 与方法说明。百万行原始业务数据仍不提交。
- CSV 明确记录 JDK、操作系统、容器限制、镜像版本及随机种子；另在说明记录 Docker Desktop 可用资源。若宿主后台负载异常或容器 OOM，应记录并重跑，不筛掉慢数据来改善结果。

## 限制和后续

这里不测 CDC 延迟、故障恢复或端到端任务 API；它们须另设实验和报告。一次性容器与本地 Docker Desktop 的磁盘缓存会影响绝对耗时；本实验提供受控对比，而不是普适性能承诺。
